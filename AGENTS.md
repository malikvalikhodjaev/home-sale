# Инструкции для работы с проектом

## Язык и стиль

- Работать на русском языке.
- Использовать понятные названия без внутренних кодов в пользовательских заголовках.
- Технические идентификаторы допустимы только там, где они действительно нужны для связи записей.

## Источники и доказательства

- Не считать старый контекст автоматически актуальным.
- Не выдавать план, чекбокс или созданный файл за достигнутый результат.
- Отделять подтверждённые факты, слова владельца, гипотезы, решения, планы и выполненную работу.
- Не заменять неизвестное нулём или догадкой.
- Для каждого существенного изменения указывать источник, дату и причину.

## Сырые материалы

- Не изменять и не перемещать оригиналы фотографий, PDF, Excel, кадастровых документов и прежних контекстов без отдельного явного запроса.
- Производные результаты сохранять новыми файлами.
- Не добавлять чувствительные документы и оригинальные фотографии в Git.

## Объявления

- `listings/canonical/` содержит только текущие принятые версии.
- `listings/archive/` содержит неизменяемые исторические версии.
- Новая публикация должна ссылаться на конкретную версию текста, цену и набор медиа.
- Изменение цены, текста или набора фотографий создаёт новую версию; старую не перезаписывать.
- Не обещать отдельный участок, полностью узаконенную фактическую площадь, собственные парковочные места или полную юридическую готовность без актуального подтверждения.

## Задачи и Git

- Оперативный статус задач ведётся в Coda.
- Git хранит рабочие продукты и историю решений.
- Выполненная задача должна иметь ссылку на файл, commit, публикацию или другое проверяемое подтверждение.
- Не публиковать репозиторий и не настраивать remote без явного решения владельца о приватности и проверки состава первого push.

## Характеристики, индикаторы и guardrails

- В каждой области одновременно улучшать ровно три характеристики и использовать ровно один guardrail.
- Guardrail не входит в число трёх улучшаемых характеристик.
- Остальные сигналы оставлять в мониторинге, только если они меняют конкретное решение; иначе не включать.
- Для каждой активной характеристики выбирать один основной индикатор.
- К подхарактеристикам и Q-Bundle применять то же правило `3 + 1` рекурсивно.
- Q-Bundle считается одной характеристикой на родительском уровне; его элементы считаются на внутреннем уровне.
- Полная спецификация: `governance/CHARACTERISTIC_SELECTION_RULES.md`.
